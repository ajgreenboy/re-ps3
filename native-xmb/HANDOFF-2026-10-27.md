## 2. What ships

What a user gets from this tree, with the limits kept in view:

- **The application is one Windows x64 executable**, `re-ps3-native.exe`, plus the Qt runtime that
  `windeployqt` copies beside it. The build also produces the `xmb-reference-frames` helper and, when
  `-SteamworksHeaders` is given, `xmb-steam-client.exe`. There is no installer. The output folder is
  portable apart from the firmware it reads.
- **Rendering**: firmware-ported background/HDR/glare, ribbon cloth and FFD sheet, 4.93 cold-boot
  intro, both particle passes (quads into the HDR scene, separate `particles_second` glare program),
  FreeType glyphs at the traced load flags with sub-pixel phase and a coverage-union mask, and
  category/item icons through the opaque normal-map material.
- **Menus**: the ten category columns, pages, information pages, dialogs, the on-screen keyboard
  (including masked password input), the item-level Triangle options menu, the PS system menu,
  notifications, the volume HUD and the in-XMB Jellyfin sign-in page. The Network column is generated
  from the firmware's own XMBML; the other columns are still hand-built.
- **Services**: Steam library/collections/store/downloads/accounts/friends (read-only handoffs, no
  purchases or downloads inside the XMB), native Jellyfin browsing and playback, local photos, music
  and video with sidecar subtitles, resume points and the Video column's Continue Watching row, plus
  the versioned imported-apps registry and editor.
- **Settings and state**: versioned `preferences.json`, `profiles.json`, theme files (`.p3t`) read in
  memory, and host-backed volume/mute/display settings.
- **What does not ship**: firmware assets (a local `dev_flash` is required and never committed),
  build outputs, reference captures, Steam artwork caches, credentials, or any diagnostic bundle.

## 3. Build, run, verify

Full one-page instructions, including prerequisites and troubleshooting, are in [INSTALL.md](INSTALL.md).
The short form, from the repository root:

```powershell
# Build. Stop re-ps3-native.exe first: the linker fails with LNK1104 while it runs.
& .\native-xmb\build.ps1
# -> out\native-xmb\re-ps3-native.exe plus the deployed Qt runtime

# Run. --dev-flash is required; without it the app prints usage and exits with code 2.
& .\run-native-xmb.ps1 -FlashRoot C:\path\to\dev_flash
# or directly:
& .\out\native-xmb\re-ps3-native.exe --dev-flash C:\path\to\dev_flash --data-dir C:\path\to\data
```

Conventions that matter:

- The default build output is `out/native-xmb` (relative to the repository root). A side build for a
  parallel session is `build.ps1 -OutputDirectory C:\dev\out\scratch`; the Qt deployment lands in that
  same folder, so it is self-contained.
- The launcher defaults `-FlashRoot` to the sibling `rpcs3\bin\dev_flash` and checks for
  `vsh\resource\explore_plugin_full.rco` before starting.
- The default data directory is `<exe folder>\data`; the launcher passes `out\native-xmb\data`.
- The launcher writes per-run `native.stdout.txt` and `native.stderr.txt` under
  `out\native-xmb\sessions\<timestamp>\`.
- Firmware and derived data stay local: `out/`, `fw493/`, decrypted modules, captures and reference
  frames are gitignored.

Verification is the maintained harness, not a new test suite:

```powershell
# Full gate: stored per-layer pair + canonical capture + four named Steam/XMB states.
& "$env:USERPROFILE\.bun\bin\bun.exe" work\ab-layers.ts --all

# One image, whole frame or a crop.
& "$env:USERPROFILE\.bun\bin\bun.exe" work\ab-compare.ts <ref.png> <native.png> [x,y,w,h]

# Machine-readable gate report.
& "$env:USERPROFILE\.bun\bin\bun.exe" work\ab-layers.ts --all --json
```

`work/release-check.ps1` wraps the release checks (gate, key scan, firmware/data scan, doc links) and
prints PASS/FAIL; see section 9.

## 4. The gate: what it covers, and today's result

`work/ab-layers.ts --all` is three gate families in one command:

1. **Stored per-layer pair.** Six named crops of the stored native root frame against the stored
   RPCS3 root frame (`out/native-reference/ab-native-root.png` vs `ab-rpcs3-root.png`), each gated at
   baseline minus 0.5 dB PSNR / 0.004 SSIM. Deterministic offline scoring; it catches decoder, metric
   and crop regressions. These are historical comparison numbers, not a fidelity claim.
2. **Canonical capture.** The same six crops on a fresh native frame with every clock pinned
   (`--render-clock 30`, `--background-clock 2026-10-25T10:00:00`, `--ui-clock 2026-10-25T12:32:00`,
   `--focus-time 2000`), an empty Steam root and the `full,wait,wait,wait` script. This is the
   regression gate for the current rendering.
3. **Four named states**: `steam-game-root`, `steam-all-games`, `steam-store-sections`,
   `steam-not-installed`. Each asserts the navigation state and exact row/detail counts from a dump,
   then scores whole-frame and content crops at PSNR >= 55 dB / SSIM >= 0.9995 against a stored
   deterministic native reference. Self-baselines catch deterministic drawing, layout and content
   changes; they say nothing about firmware fidelity.

Exit codes: 0 all gates pass, 1 a metric gate failed, 2 a state assertion or input/runtime error.

## 6. Config migration policy (Phase 7.3)

The rule: **state is versioned, migrations move forward only, and an unknown/newer file is preserved,
never rewritten.** This describes the committed implementation at `0c8faee`; the in-flight source
edits in the shared tree may change it, so re-read `src/preferences.cpp` and `src/profiles.cpp`
before citing line-level behaviour.

- **Versioned documents.** `preferences.json` is `{"version":1,"values":{...}}`; `profiles.json` is
  `{"version":1,"profiles":[...],"activeId":"..."}`; the imported-apps registry is
  `{"version":1,"apps":[...]}`. `work/ab-layers.thresholds.json` carries its own
  `xmb-per-layer-thresholds/1` schema string for tooling. The version is inside the document, not in
  the file name.
- **Forward-only.** A reader accepts the versions it knows and migrates them in memory, then writes
  the current version. It never writes an older version and never half-migrates: writes go through
  `QSaveFile` (`commit()`), so the old file survives an interrupted write. A legacy `settings.ini` is
  read once into the versioned preferences and deliberately left on disk.
- **Downgrade behaviour.** A file with an unknown or newer version, invalid JSON or an invalid shape
  becomes read-only: the existing bytes are preserved, the app reports that it has preserved them,
  and no default is written over them (`Preferences::writable_ = false`,
  `"Preferences have an invalid or newer format. The existing file has been preserved."`;
  `Profiles` applies the same rule). Values inside a known version that fail validation are dropped
  from the in-memory map, which is why a migration must widen the reader before the writer narrows.
- **The resume-record migration is the template.** The 2026-10-26 change (`a0bd0b0`) replaced bare
  `{"<sha1>": milliseconds}` resume entries with records
  `{"<sha1>": {"path","ms","dur","title","at"}}`. The old shape was kept valid in
  `Preferences::valid()` so loading would not discard it before migration; `Shell::migrateResumePoints()`
  then resolved the old entries by hashing the configured libraries, dropped unresolved ones with a
  stated reason, and all later writes used the new shape. That is the order to copy:
  1. widen the reader to accept the old and new shapes;
  2. migrate on load in a bounded pass, with an explicit rule for entries that cannot be resolved;
  3. keep the old file/value until the new one has committed;
  4. only then narrow the writer, and bump the document version only when accepting both shapes in
     one reader is no longer practical;
  5. record the change in [ISA.md](ISA.md) decisions and add a gate or fixture that feeds the old
     shape in and asserts the new shape out.
- **Invalid input is never "repaired" silently.** A corrupt or newer file is reported and preserved;
  the app continues with defaults in memory and will not save over it. Users who downgrade therefore
  lose no data and can move back up without a hand edit.

## 7. Diagnostics and crash reporting (Phase 7.2)

- **Diagnose design**: [audit/DIAGNOSE.md](audit/DIAGNOSE.md) specifies a `--diagnose` bundle - what
  it collects, the redaction rules (never credentials, the Steam Web API key or Jellyfin tokens), a
  5 MiB size cap and the write location. It is a design, not an implemented flag: no shell or view
  changes were made in this pass. A standalone `work/diagnose.ps1` collector is the intended next
  step if the app-side flag is not wanted.
- **Crash reporting already ships.** `main.cpp` installs a Windows unhandled-exception filter that
  appends the exception code and a symbolized stack (up to 40 frames, using the `.pdb` next to the
  executable) to `XMB_LOG` when that variable is set, otherwise to `crash.log` beside the executable.
  It is local-only: no upload, no telemetry, no credentials.
- **Logs**: `XMB_LOG=<file>` appends every Qt message; `XMB_FRAME_TRACE=<file>` records a bounded
  frame trace on orderly shutdown; the `XMB_*_LOG` variables add service-specific lines. The launcher
  captures stdout/stderr per session.

## 11. Ground rules for the next session

- **Read before writing.** `git log -1` and `git status --short` first; this tree is shared and HEAD
  or the working set may have moved since this file was written.
- **Never commit firmware or derived data.** `fw493/`, `boot/`, `out/`, decrypted modules, RCO dumps,
  reference frames and captures are gitignored for a reason.
- **No new test suites** unless asked: `work/ab-layers.ts`, `work/ab-compare.ts` and the `--script`
  captures are the maintained path.
- **Builds**: stop `re-ps3-native.exe` before linking; parallel sessions use separate
  `-OutputDirectory` values; scripted verification needs `--dev-flash`, and usually `--no-intro`.
- **Tooling**: Bun/TypeScript for `work/*.ts`; PowerShell is fine for one-off commands. No Python
  without approval.
- **Style**: match the file you are editing; user-visible strings go through `QObject::tr()` (or the
  file's existing string idiom), no new third-party dependency without a reason, and docs are ASCII
  markdown with relative links and a dated status line.
- **Credentials**: the Steam key lives outside the repo; Jellyfin session tokens stay in memory; no
  key or token goes into preferences, reports, manifests, logs or docs.
- **Writes**: documentation and `work/` helpers are cheap; source, thresholds and the harness are not.
  Keep the write fence explicit when handing work to another agent.
- **Pushing** is a separate, approved operation. The local `origin/main` may lag the real remote
  until a fetch; say so rather than claiming a push state.
