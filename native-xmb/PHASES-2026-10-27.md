# Implementation phases, 2026-10-27

Supersedes the phase list in [HANDOFF-PHASES.md](HANDOFF-PHASES.md) as the forward plan; that file stays as
the record of the 2026-10-25/27 phase pass. The gap register it was written against is
[audit/FIRMWARE-PARITY-GAPS.md](audit/FIRMWARE-PARITY-GAPS.md); the HTPC ideas queue is
[audit/HTPC-IDEAS.md](audit/HTPC-IDEAS.md).

## Where the project actually is

- **Rendering**: background/HDR/glare, ribbon, cold boot and both particle passes are firmware ports; glyphs are
  FreeType coverage at the traced load flags with sub-pixel phase and a coverage-union mask; category and item
  icons draw through the firmware icon program's material (opaque approximation, glass path diagnostic-only).
- **Menus**: category columns, pages, information pages, dialogs, OSK (with masked input), the Triangle options
  panel, the PS system menu (captured from RPCS3), notifications, the volume HUD and the in-XMB Jellyfin sign-in
  page all exist. The Network column is generated from firmware XMBML; the other columns are still hardcoded.
- **Services**: Steam library/collections/store/downloads/accounts/friends (read-only, honest handoffs), native
  Jellyfin playback with sign-in and - in flight - resume/played state, local media with subtitles, resume and
  Continue Watching.
- **Verification**: `work/ab-layers.ts --all` (6 layer gates, canonical capture, 4 named states) is green; the
  harness is the only test suite by design.

Honest score against the firmware target is still the register's ~47% band: the remaining half is mostly
*rendering materials*, *firmware-driven menus*, and *behaviours with real backends* (audio mixing, profiles,
disc/media services), not missing scaffolding.

## Phase 1 - Jellyfin completion (finish the in-flight slice, then breadth)

**Goal**: Jellyfin is a complete couch media path with the state a user expects from a client.
**Why now**: the parallel session's resume/played/restart slice is uncommitted and unverified; everything else
here builds on it.

- 1.1 Verify and land the in-flight slice (resume from `UserData.PlaybackPositionTicks`, "Resume at", "Play from
  Beginning", completed -> Watched, progress/stop reporting). *S*
- 1.2 Posters and backdrops: fetch `Primary`/`Backdrop` images through the authenticated image endpoint, decode
  bounded, cache locally per item, use them as the row icon and the page/hero backdrop. *M*
- 1.3 Search: a Jellyfin search page driven by the existing OSK, results as rows with the same Play/Resume
  semantics. *M*
- 1.4 Stream subtitle/audio tracks: list `MediaStreams` from `PlaybackInfo` and expose the ones the player can
  switch; disable the rest with a reason (same honesty rule as the local player panel). *M*
- 1.5 Remembered sign-in behind DPAPI, with an explicit "stay signed in" choice and a threat-model note. *M*

**Exit criteria**: with a disposable server, a resumed item starts at the server-reported position (sidecar
`mediaPosition` within 2 s), a finished item shows Watched and reports stop at the end, a restarted item starts at
0, posters render for at least one item, search returns rows, and a failed stream shows the client's error.
**Evidence**: scripted captures + sidecars + server log, as in `audit/JELLYFIN-NATIVE.md`.
**Needs**: one disposable Jellyfin server run (the previous one was not kept) and the user's server only if they
want their own library tested.

## Phase 2 - Rendering parity II: materials, not scaffolding

**Goal**: close the remaining layer gaps that the register still scores low, each with measured evidence.
- 2.1 Item icons through the refractive glass path for every icon class (not just `icontex`), including the
  captured `_Ambiant.w`-on-alpha semantics once refraction exists. *L*
- 2.2 Category icon material: replace the opaque approximation with the firmware glass program driven by the
  traced `ICONS.mnu` constants and the month palette; keep the opaque path as the fallback. *L*
- 2.3 Particle shading finish: positional spot (SPOT POS), the untraced `_Color`/`_Gamma` terms, life-bounds and
  near/far darkness, and the blending mode question (qgl material mode). *M*
- 2.4 Text finish: PAF advance/metrics authority (the clock advance already agrees within 0.06 px; extend to all
  labels), the elision rule wired from `elideToWidth`, caret/cursor metrics, and the label glow parameters. *M*
- 2.5 UI-layer glare: the firmware blooms the UI through the same glare chain; measure and decide whether the UI
  layer belongs in the glare source (currently it is composited after tone mapping). *M*

**Exit criteria**: each sub-item either improves its layer(s) beyond the 0.5 dB / 0.004 budget or is reverted with
the measured reason; the register's rendering score is re-scored with citations.
**Evidence**: `work/ab-layers.ts --capture` per layer, item-icon crops (new layers: icon interior / icon edge),
particle crop under `--render-clock`.
**Needs**: none beyond the local dev_flash captures already present.

## Phase 3 - Firmware-driven menus and behaviours

**Goal**: the columns and behaviours come from the firmware's own definitions, and the missing list actions are
honest.
- 3.1 XMBML-driven columns for user/settings/photo/music/video/game/psn/friends (the reader exists; Network
  proved it). Fall back row-by-row, log the source. *L*
- 3.2 Options-menu breadth: implement the list actions a local library can honestly support (Sort By is done;
  next: Display All for a folder page, Copy/Move for local libraries with progress, Delete with confirmation) and
  keep unsupported firmware rows absent rather than stubbed. *L*
- 3.3 Information-panel indicators: friends online count, new-message/notification counters, What's New, driven
  by the services that already exist; no fabricated network events. *M*
- 3.4 Notification breadth: the notification sound (needs a firmware cue and mix evidence), per-type suppression
  (trophy/download/message), overlap policy with the volume HUD and the PS menu. *S*
- 3.5 Background music: a music source (local library playlist or Jellyfin audio) with crossfade/ducking rules and
  a settings toggle; the firmware's BGM behaviour is only partially evidenced, so start with an explicit toggle
  and document the uncertainty. *M*
- 3.6 Profiles: per-user preferences and a profile switch (the console's Users column), replacing the single
  shared `Preferences` object. *L*

**Exit criteria**: a column built from XMBML matches its firmware row list (dump + state assertion); each new
options action works on a fixture and is reversible; indicators show real counts; the BGM toggle audibly plays
and stops with no cue overlap bug; profiles store separate settings and switch without restart.
**Evidence**: named states per column/panel + dump assertions; `XMB_*_LOG` traces; a PSNR-regression baseline for
each new surface.
**Needs**: user input for the profile UX and the BGM source; audio verification needs ears or a recorded mix.

## Phase 4 - Session and power behaviour (HTPC)

**Goal**: the app behaves like an appliance on a TV.
- 4.1 Auto-Off goes dark instead of quitting to the desktop; the display-awake hold extends to launched titles
  (already proven for media). *S*
- 4.2 A launcher/kiosk mode: fullscreen on a chosen display, no title bar, start with Windows optionally,
  controller-only exit path. *M*
- 4.3 Controller status page: which pad is attached, battery/charge, mapping; reuse the PS-menu controller panel.
  *S*
- 4.4 Safe-area and UI scale options for overscanning TVs (the layout is fixed 1920x1080 today). *S*
- 4.5 An optional PIN gate for settings/purchases-free surfaces, stored hashed, local only. *M*

**Exit criteria**: a 30-minute idle TV session dims and wakes pixel-identically (the existing idle gate), a title
launch keeps the display awake, kiosk mode starts and exits with the controller, the controller page shows the
attached pad, overscan margins are configurable and persist, and the PIN gate blocks with a verified hash.
**Evidence**: scripted `idle=` captures, `pcocfg`/powercfg read-only checks, capture at two UI scales.
**Needs**: a controller for the pad checks (the current machine has a DualSense; HID paths were never physically
pressed in tests).

## Phase 5 - Verification and performance hardening

**Goal**: the harness covers every new surface and the app survives real sessions.
- 5.1 Named states for the new surfaces (options panel, notifications, volume HUD, subtitles, Continue Watching,
  Jellyfin pages/sign-in, download page) with dump assertions and deliberate references. *M*
- 5.2 A ten-minute human session crossing media, a launched title and the PS menu; record memory/fps/crash. *S*
- 5.3 Frame pacing at 60/120 Hz TV outputs: measure swap intervals with the existing frame trace, not just the
  loop rate. *M*
- 5.4 Startup budget: keep first frame under the current ~1 s with the full Steam/Jellyfin/XMBML loaders, and
  log the breakdown. *S*
- 5.5 Soak: a two-hour scripted session with media and page churn for leak detection. *S*

**Exit criteria**: every new surface has a green state gate; the ten-minute and two-hour sessions show no crash,
no growth trend and no unbounded queue; swap p95 is inside the display's frame interval at both rates; first frame
stays within budget.
**Evidence**: the harness plus the frame trace; documents in `audit/VERIFICATION-HARNESS.md`.
**Needs**: a 120 Hz display for 5.3 if one is available.

## Phase 6 - Services breadth (honest, read-only where possible)

**Goal**: close the remaining service gaps without fabricating anything.
- 6.1 Steam: account-switch UI over the existing plan, store free-text search through the OSK, a "Continue
  Playing" Steam equivalent, verified launch+quit lifecycle on a real title (the `+app_stop` path is unproven
  against a live game). *M*
- 6.2 Steam friends: avatars and richer game names (bounded downloads), and the documented Web-API fallback
  limits. *S*
- 6.3 Trophy support: the trophy list is currently a placeholder; either implement a local trophy view for
  imported titles or state clearly that no backend exists. *M*
- 6.4 Network column rows: manual/browser/search/Remote Play stay honest `Unavailable` rows until a real backend
  exists; if a local browser handoff is desired, make it an explicit app registration instead. *S*
- 6.5 Disc/media services: document them as unsupported on a PC (no BD drive integration planned) so the XMB
  rows are honest. *S*

**Exit criteria**: each item either works end to end with evidence or is documented as unavailable with the reason
shown in the UI; no row claims a capability the build lacks.
**Evidence**: CLI reports, scripted captures, one real Steam title launch/quit if the user agrees.

## Phase 7 - Packaging, operations and handoff

**Goal**: someone else can install, run, diagnose and continue this.
- 7.1 A portable release folder (exe + Qt runtime + docs) and a one-page install/run guide, including the
  `--dev-flash` requirement and where the data directory lives. *S*
- 7.2 Crash reporting and a bounded diagnostic log bundle (never containing credentials), plus `--diagnose`. *M*
- 7.3 Config migration policy and versioned preferences (the resume-record migration is the template). *S*
- 7.4 A fresh current handoff (the last snapshot is now historical) and a short contributor guide: build, test,
  capture, style conventions. *S*
- 7.5 Release checklist: gate green, key scan clean, docs current, firmware data excluded. *S*

**Exit criteria**: a clean machine builds and runs from the guide; `--diagnose` produces a bundle that explains a
failure without secrets; a fresh handoff is accurate on the day it is written.
**Evidence**: a from-scratch build/run walkthrough and the checklist.

## Sequencing recommendation

1. **Phase 1** first: the in-flight slice is uncommitted and blocks nothing else, and it completes a user-facing
   feature.
2. **Phase 5.1** in parallel with 1 and 2: each new surface needs its gate before more surfaces pile up.
3. **Phase 2** next: materials are the largest remaining score gap and everything is local.
4. **Phase 3** then **Phase 4**, with the profile/UX decisions taken from the user before 3.6 and 4.2.
5. **Phase 6** whenever a real Steam title/Jellyfin server run is acceptable.
6. **Phase 7** last, so the guide describes the finished build.

## What this plan deliberately excludes

- **Dynamic theme animations** (`.p3t` RAF scenes): the parser work in `audit/THEMES.md` shows this is a new
  subsystem (Edge geometry, skinning, VSMX, the effect set), size L-weeks; the honest current behaviour is a
  static theme background and that stays until someone funds the subsystem.
- **In-game XMB overlay** beyond the PS-menu quick actions: the firmware overlay is a separate render of the full
  XMB over the game; recreating it needs an injection/host path this project has deliberately avoided.
- **Disc, PSN/online services, chat, purchases**: no backend exists or should be fabricated.
- **Shell replacement / global hotkeys / HDMI-CEC**: outside the app's scope and, for CEC, unsupported hardware.
